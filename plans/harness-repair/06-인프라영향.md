## 2. 금전 비용 — 제약이 아니다

턴당 실측 **$0.005470**, 그중 **gpt-4o 메인 LLM이 96.0%**.

| 항목 | 변경 | 턴당 델타 |
|---|---|---|
| **P2-2** 게이트 확대 | InputJudge 호출률 0.20 → 0.80 (4배) | $0.000030 → $0.000120 = **+$0.000090** |
| **P1-2** 구분자·지시계층 | 프롬프트 +40~80 tok | **+$0.00002** |
| **P2-4** 근거 span 출력 | Judge 출력 증가 | **+$0.00003** |
| **P3-2** Judge 맥락 | Judge 입력 470 → ~1,000 tok | **+$0.00004** |
| P0-1 · P0-3 · P1-1 · P1-3 · P1-4 · P2-3 · P3-1 | 결정론 로직·DB 필드 | **$0** |
| **합계** | | **약 +$0.00018 = 턴당 +3.3%** |

세션 12턴 $0.0670 → 약 $0.0692. **로드맵의 비용 게이트(+20%p 호출률)보다 훨씬 작다.**

> **⚠ 먼저 해소할 수치 불일치**: cost baseline은 InputJudge 호출률을 **0.20**으로 잡았는데,
> safety-hybrid·침투 문서는 **65.1%**를 쓴다. 전자는 튜닝 목표(15~25%), 후자는 #258 이후
> 코퍼스 측정값이다. **프로덕션 실값은 `trace.input_judge_called` 집계로 확인해야 한다** —
> 그것 없이는 P2-2의 목표("호출률 ≤ 80%")가 기준점을 갖지 못한다.
> P0-3보다 먼저 할 수 있는 한 줄 쿼리다.

## 3. 지연 — 유일한 실질 충돌

### 세 작업이 같은 동기 경로를 다툰다

`ConversationOrchestrator.handle` → `buildContextSync` 는 **유저 대면 동기 경로**다.
여기에 세 가지가 동시에 얹히려 한다.

| 출처 | 내용 | 델타 |
|---|---|---|
| **F2 조치** (실사진단 권고) | 임베딩 상한 250ms → **600~800ms** 재설정 | 매 턴 **+350~550ms 무조건** |
| **P2-2** | InputJudge 호출률 상승 | 스트리밍 없는 JSON 완성, **p95 3,048ms**가 더 많은 턴에 붙는다 |
| **P3-2** | Judge 입력 470 → ~1,000 tok | Judge 자체 지연 증가 |

현재 임베딩은 **54/57턴이 타임아웃**되어 250ms를 매 턴 버리고 있다.
F2를 고치면 그 250ms가 실제 대기로 바뀌고 상한이 2~3배가 된다.

### 조치 — 통합 지연 예산

**개별 항목에 "p95 +15% 이내"를 각각 걸면 셋이 합쳐 +45%가 된다.**
[04-개선설계](04-개선설계.md)의 중단 조건을 항목별에서 **통합 상한 하나**로 바꾼다.

| | 값 |
|---|---|
| 대상 지표 | **첫 실질 토큰 지연 p95** (`trace.first_substantive_token_ms`) |
| 통합 상한 | **현행 기준선 대비 +20% 이내** — F2 · P2-2 · P3-2 **합계** |
| 배정 순서 | F2 먼저(품질 결함 수정, 되돌릴 수 없는 손실) → 남은 예산으로 P2-2 → 그 다음 P3-2 |
| 하드 상한 | `SseEmitter` **60s** / nginx **90s**. 첫 토큰 3~4초는 타임아웃엔 안 걸리지만 체감이 걸린다 |

### 완화 자산이 이미 있다

`safePrefixDelivery`가 서버 고정 문구를 **먼저** 보내 첫 화면 표시 지연을 끊어낸다.
**P2-2를 진행할 때 safe prefix 커버리지를 함께 봐야 한다** — 커버리지가 낮은 경로에서
Judge 호출률을 올리면 사용자가 빈 화면을 더 오래 본다.

### 부하 테스트 주의

실사진단 §3.5: *"부하 테스트를 설계할 때 사용자 트래픽만 넣으면 실제 주부하를 빠뜨린다.
잡 8개가 겹치는 구간을 반드시 포함해야 한다."*
스케줄 작업이 **HTTP 요청 3,516건 대비 26,248회** 실행된다.
**P2-2의 지연 측정을 사용자 트래픽만으로 하면 무효다.**

## 4. 메모리 — 관측 스택은 물리적으로 막혀 있다

### 내 문서의 오류

[04-개선설계 P0-3](04-개선설계.md)에 *"P0-9의 Prometheus·Grafana·Alertmanager 스택이 이미 있다"*
고 썼다. **정정한다** — 저장소에는 있고(`docker-compose.observability.yml` + `ops/observability/`,
Prometheus 룰 10종 준비) **배포되지 않았으며, 현 인스턴스에 얹을 수 없다.**

| 배치안 | 컨테이너 | cap | shim | 실효 예산 | 판정 |
|---|---:|---:|---:|---:|---|
| 전체 (prometheus + alertmanager + grafana) | 3 | 448MB | 60MB | 213.8MB | **부족 234.2MB** |
| Grafana 제외 | 2 | 256MB | 40MB | 233.8MB | **부족 22.2MB** |

신규 컨테이너 안전 예산은 **273.8MB**다(`1,841 − 319.2 비컨테이너 − 1,248 기존 cap`).
`mem_limit`은 2026-08-07 페이지 캐시 스래싱 장애의 재발 방지 장치이므로,
**모든 컨테이너가 동시에 상한까지 올라가도 물리 RAM에 들어와야** 그 보호가 성립한다.
CD도 관측 스택을 배포하지 않는다(`cd.yml:123`이 `docker-compose.prod.yml` 하나만 쓰고,
관측 스택은 `profiles: ["observability"]`로 게이트).

### P0-3의 실행 경로를 바꾼다

**Prometheus 메트릭이 아니라 `ai_policy_decisions.trace` SQL 집계로 시작한다.**

| | |
|---|---|
| 비용 | **0** — `trace`는 `JSONB NOT NULL DEFAULT '{}'`(`V8__init_ai_memory.sql:73`), 마이그레이션 불필요 |
| 배포 의존 | **없음** — 관측 스택 배포를 기다리지 않는다 |
| 충분한가 | **그렇다.** 보안 축 지표에 필요한 것은 실시간 알람이 아니라 **배포 전후 비교**다. `SELECT trace->>'crisis_attribution', count(*) … GROUP BY` 로 산출된다 |
| Prometheus는 언제 | **L4(HikariCP 풀 20 → 8) 이후.** 풀을 내리면 PG cap 하한이 208 → 160MB로 내려가 cap을 320 → 192MB로 정정할 수 있고 **128MB가 회수된다.** 그때 Grafana 제외 안이 여유 89.8MB로 들어간다 |

즉 **관측 스택 배포는 내 계획의 선행 조건이 아니고, L4가 그 선행 조건이다.**
순서를 뒤집으면 P0-3이 배포 불가 항목에 묶인다.

### metaspace — 신규 클래스에 주의

이 앱의 OOM 경로는 힙이 아니라 **metaspace**다(140.2MB, 상한 없음, `MaxRAMPercentage`는 힙만 규율).
app cap 800MB에 JVM 최악 742.3MB → **여유 57.7MB**.

내 항목은 대부분 기존 클래스 수정이고 신규는 P1-1의 n-gram 검사기, P3-1의 누적기 정도로
클래스 몇 개 수준이다 — **무해하다.** 다만 새 라이브러리를 끌어오는 선택은 이 예산에 직접 걸린다.

### P1-1 ①의 할당 패턴 — 캐시 필수

n-gram 유출 탐지는 시스템 프롬프트에서 창을 뽑아 집합을 만든다.
프롬프트 ~1,500 tok에서 12자 창이면 **수천 개 String**이다.
**턴마다 재생성하면** SerialGC + 힙 425MB에 불필요한 압력을 준다.

> 베이스 프롬프트는 **캐릭터 × 모드별로 고정**이고 메모리·체크포인트 블록만 턴마다 변한다.
> → 고정부 n-gram 집합은 캐시하고, 가변부만 턴당 계산한다.
> 이러면 턴당 비용이 O(응답 길이)로 떨어진다.

## 5. 자체 호스팅 분류기는 불가능 — P3-4 수정

[04-개선설계 P3-4](04-개선설계.md)가 Qwen3Guard·OpenGuardrails를 후보로 올렸다.
**t4g.small에서 자체 호스팅은 물리적으로 불가능하다.**

| 후보 | 가중치 (FP16 기준) | 신규 컨테이너 예산 273.8MB 대비 |
|---|---|---|
| Qwen3Guard 0.6B | ~1.2GB | **불가** |
| Qwen3Guard 4B / 8B | ~8GB / ~16GB | **불가** |
| OpenGuardrails 3.3B GPTQ | ~2GB+ | **불가** |

총 RAM이 1,841MB이고 그중 1,567.2MB가 이미 cap으로 묶여 있다.
게다가 GPU가 없고 2 vCPU Graviton2다 — 돌아간다 해도 지연이 논문의 P95 274.6ms(로컬 GPU 기준)와
무관해진다.

### 남는 선택지 셋

| | 선택 | 평가 |
|---|---|---|
| **A** | **오프라인 평가 전용** — `security-eval-v1` 채점 보조로만, 런타임 경로에 넣지 않는다 | **권장.** 인프라 부담 0, 라벨 품질 향상. 상용 라이선스(Apache-2.0)라 가능 |
| B | 외부 추론 API로 호출 | 지연 예산(§3)에 또 얹히고, 한국어 대화 원문을 제3자에 보내므로 §10.4 프라이버시·불변식 19 검토 필요 |
| C | 포기 | 허용 가능 — 이 항목은 P3이고 [총괄](README.md)의 "경계가 아니다" 판정을 받았다 |

**A로 확정하는 것을 권한다.** 런타임 도입은 인스턴스 상향이 결정된 뒤에 재검토한다.

## 7. ★ 순서 강제 — F1·F2가 두 보안 항목의 트리거다

이번 검토의 가장 중요한 발견이다.

### F1 → P1-3 ② (체크포인트 스캐너 편입)

> **F1 — 대화 체크포인트는 프로덕션에서 한 번도 저장된 적이 없다** (심각도: 치명)
> `ConversationCheckpointService:144`의 `(OffsetDateTime) row.get("created_at")` 캐스팅이
> **항상 실패**한다(PG JDBC는 `java.sql.Timestamp` 반환). 임계치 도달 2세션 모두 실패 **2/2**.
> `select count(*) from session_checkpoints` → **0**

즉 **MINJA식 지속형 메모리 오염의 현재 노출은 0**이다.
[01-진단 §5](01-진단.md)가 지적한 "사용자가 20턴 안에 심어 둔 문장이 요약을 통해 이후 모든
턴의 시스템 프롬프트에 상주한다"는 경로가 **아직 열리지 않았다.**

**그러나 F1을 고치는 순간 열린다.** 그리고 F1은 반드시 고쳐야 하는 기능 전면 불능 결함이다.

> **→ P1-3 ②는 F1 수정과 같은 PR이거나 그보다 먼저여야 한다.**
> F1만 먼저 고치면, 스캔되지 않는 경로가 프롬프트에 상주하는 상태가 그 시점에 활성화된다.

### F2 → P1-4 (캐시 폴백 highRisk 재필터)

> **F2 — 임베딩 대기 250ms가 실제 응답 시간보다 짧아, 벡터 검색이 거의 항상 버려진다**
> 타임아웃 54회 / `message_turns` 57행 → **시도된 턴의 사실상 전부**.
> `memory_embeddings` **0행**.
> 조치 권고: 상한 600~800ms 재설정.

`memory_embeddings`가 0행이므로 캐시에도 내용이 거의 없다 →
[01-진단 §3.2](01-진단.md)의 캐시 폴백 우회도 **현재 노출이 낮다.**

**그러나 F2를 고쳐 상한을 올리고 기억이 쌓이면 즉시 활성화된다.**

> **→ P1-4는 F2 수정과 함께 계획한다.** 그리고 F2 조치는 §3의 지연 예산 첫 배정 대상이다.

### 정리

**두 프로덕션 결함이 지금 내 보안 항목 두 개의 노출을 가려주고 있다.**
이건 안심할 근거가 아니라 **순서를 정하는 근거**다 —
결함 수정이 곧 공격 표면 개방이므로, 그 PR에 방어가 동반되어야 한다.
